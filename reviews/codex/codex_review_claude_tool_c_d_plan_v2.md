# Review: Claude Tool C/D Plan v2

**Grade: NEEDS CHANGES**

The v2 plan correctly fixes the v1 blockers: benchmark histories are now actually persisted by the options phase (`golden_vector/ingestion/options_phase.py:171`, `golden_vector/ingestion/options_phase.py:292`), and Tool C no longer depends on a phantom weekly-return artifact because the foundation manifest exposes the daily normalized equity snapshot (`golden_vector/app/latest_data.py:57`, `golden_vector/app/latest_data.py:77`). The remaining issues are not about scope taste; they affect whether the new rankings are analytically consistent and replayable.

## Findings

1. **[P1] Tool D's gold-price baseline is inconsistent with the Tool B context it re-exports.** The plan says Tool D reads `tool_b_latest.parquet` plus manual store plus "spot gold" (`reviews/codex/claude_tool_c_d_plan_v2.md:35`, `reviews/codex/claude_tool_c_d_plan_v2.md:148`) and calls out latest foundation gold as the spot source (`reviews/codex/claude_tool_c_d_plan_v2.md:213`). But Tool B already resolves a user/config gold-price assumption in the CLI (`golden_vector/cli.py:815`) and persists that value in every Tool B row (`golden_vector/screening/pipeline.py:319`). If Tool D re-exports Tool B valuation context while computing margin stress from a different latest foundation spot, the row mixes two gold-price bases. The plan needs one authoritative baseline: either use Tool B's persisted `gold_price_assumption` for aligned Tool D stress, or explicitly label Tool D as a fresh-spot overlay and include source/date fields that make the mismatch visible.

2. **[P1] The Option Trading wire-in needs a freshness gate, not just a cache-key change.** Phase 2 says to load `tool_c_latest.parquet`, join by ticker, and include the Tool C run id in the composite cache key (`reviews/codex/claude_tool_c_d_plan_v2.md:167`, `reviews/codex/claude_tool_c_d_plan_v2.md:202`). That only invalidates the cache when Tool C itself changes. It does not prevent a stale Tool C ranking from being used after a fresh `update-data` / `tool-a` run, even though the current loader already keys the tab on options and Tool A/B refresh ids (`golden_vector/serve/option_trading_data.py:189`, `golden_vector/serve/option_trading_data.py:293`). Since Tool C declares `source_tool_a_run_id` in its schema (`reviews/codex/claude_tool_c_d_plan_v2.md:99`), the UI plan should require that Tool C's source Tool A run matches the current Tool A output before it becomes the default sort. Otherwise fall back to down-beta with a visible stale-Tool-C note.

3. **[P1] Tool D can mix current manual data with an older Tool B snapshot.** Tool B reads manual screening data at run time (`golden_vector/screening/pipeline.py:103`) and persists derived context such as verdict, leverage, FCF yield, and missing fields (`golden_vector/screening/pipeline.py:315`). The v2 plan then has Tool D read `tool_b_latest.parquet` and the live manual store again (`reviews/codex/claude_tool_c_d_plan_v2.md:35`, `reviews/codex/claude_tool_c_d_plan_v2.md:148`). If Emanuel edits AISC, production, debt, or EBITDA after Tool B ran, Tool D will combine old Tool B context with new manual inputs. The plan should lock source precedence: either Tool D consumes manual fields already persisted in Tool B output, or it records and surfaces that it is using a newer manual-store snapshot than Tool B.

4. **[P1] The rank formulas are still underspecified, especially Tool D.** The plan says ranks are the percentile of equal-weighted robust component percentiles (`reviews/codex/claude_tool_c_d_plan_v2.md:130`, `reviews/codex/claude_tool_c_d_plan_v2.md:161`), but it does not list the exact component set, direction, and missing-value reweighting per tool. Tool C likely needs high-risk orientation for down-beta, downside volatility, relative weakness, and hit rate; Tool D has mixed directions where high AISC ratio is risky but low headroom is risky. This should be explicit in config/tests before implementation, otherwise a generic percentile helper can silently rank the wrong end of a metric.

5. **[P2] Replay provenance is path-level in the plan, but current replay verification is snapshot/hash-level.** The plan says `update_manifest_with_tool_c/d` will record consumed source paths (`reviews/codex/claude_tool_c_d_plan_v2.md:26`, `reviews/codex/claude_tool_c_d_plan_v2.md:150`, `reviews/codex/claude_tool_c_d_plan_v2.md:201`). Existing replay verification checks copied snapshots and hashes for configs, manual data, foundation manifest, and options manifest (`golden_vector/app/replay_manifest.py:185`, `golden_vector/app/replay_manifest.py:217`). Recording `latest.parquet` paths is not enough because latest files are mutable. The plan should say which Tool A/B/source assets are copied into the run's replay snapshot area, what hashes are stored, and how `verify_manifest` will validate them.

6. **[P2] Weekly-return conventions need the actual source columns and early-window behavior.** v2 correctly says Tool C resamples daily foundation equities itself (`reviews/codex/claude_tool_c_d_plan_v2.md:21`, `reviews/codex/claude_tool_c_d_plan_v2.md:140`), and the foundation manifest exposes raw gold plus normalized equity snapshots (`golden_vector/app/latest_data.py:53`, `golden_vector/app/latest_data.py:57`). The plan still leaves implementation to choose price columns and rolling-window behavior. It should pin equity, gold, and benchmark price columns, plus what happens before the 156-week regime window is available (`reviews/codex/claude_tool_c_d_plan_v2.md:155`). That is load-bearing because risk #1 is consistency with Tool A's beta windows.

7. **[P2] Operational refresh/status behavior is not covered after making Tool C a UI default.** The plan adds `tool-c` and `tool-d` CLI commands but does not say whether `python main.py refresh` and `python main.py status` include or report them. Today refresh stops at Tool B (`golden_vector/cli.py:1695`) and status only summarizes foundation, Tool A, and Tool B (`golden_vector/cli.py:1743`). If the Option Trading tab defaults to Tool C when present, the operational path must either refresh/report Tool C or clearly mark it optional and stale-aware. Otherwise users can believe the tab reflects the latest refresh while it is ranking on an older Tool C output.
