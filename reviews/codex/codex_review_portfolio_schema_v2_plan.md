# Review - Portfolio Store Schema v2 Plan

**Verdict:** NEEDS CHANGES

The plan identifies the correct root problem: the current manual lot model cannot represent a GBP broker cost basis for an AUD/CAD/USD-quoted security. I verified that directly: `PortfolioLot` stores only `buy_currency`, `cost_local` is `shares * buy_price`, and `validate_lot_input` rejects any currency that differs from the ticker's configured quote currency. The proposed direction is right, but the plan is not build-ready yet because Option A leaves too many existing artifact and UI fields with ambiguous or wrong meanings.

## Answers To The Plan's Open Questions

1. **Option A vs B first:** Do not ship the current Option A as written. A smaller-than-B version is fine, but it must include explicit `quote_currency`/`cost_currency` fields and retire ambiguous local P&L for mixed-currency rows. That is closer to "Option A+" than pure Option A.
2. **Base currency:** Keep USD internally for now, but compute GBP presentation fields in the backend. Do not do display-layer FX arithmetic in serve.
3. **Out-of-universe holdings:** Prefer a portfolio-only instrument registry over polluting the analytical universe. It can value ETFs/other equities without making Tool A/B/C/D believe they are gold miners.
4. **Dual listings:** Yes, store SRB and SBI as separate source lots mapped to canonical `SRB.L`, with raw broker symbol preserved. Aggregate for analytics, keep source lines for reconciliation.
5. **FX for cost:** Reuse the existing FX history and `merge_fx_asof`, but the portfolio pipeline needs access to raw FX history first. Current `LatestFoundationSnapshot` does not expose it.
6. **Hidden consumers:** Yes: `portfolio_page.py`, `m4_artifacts.py`, `reconciliation.py`, `reader.py`, model-state artifact schema, and tests all consume the current `buy_currency`/`cost_local` semantics.

## Recommended Revised Sequence

1. Schema v2 design pass: define exact store fields and artifact columns, including quote currency, cost currency, source provenance, and base-currency P&L fields.
2. Backend FX lookup: expose cost-currency FX from the current foundation manifest using the existing `merge_fx_asof` helper.
3. Store migration + valuation: migrate v1 lots to v2, compute cost USD/GBP separately from quote value, and suppress local P&L where currencies differ.
4. Artifact schema bump + stale handling: bump `PORTFOLIO_SCHEMA_VERSION`, update readers and UI rendering to fail calm on stale artifacts.
5. Snowball dry-run v2: change the importer to treat Snowball currency as cost currency and prove AUD rows become representable without writing the store.
6. Only then build the atomic full-replacement writer and reconciliation signoff.

The plan is directionally correct, but I would not code from it until the field semantics and FX source path are tightened. Otherwise we risk making the portfolio page render plausible-looking but mathematically invalid P&L.
