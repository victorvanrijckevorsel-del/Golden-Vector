# Codex Review - Portfolio Schema v2 Checkpoint 1, Increments 1-2

Verdict: **NEEDS CHANGES before Increment 3**

Valid v1 lots migrate safely in memory, `load_lots()` does not rewrite on read, the FX foundation is correctly additive, and the new dataclass fields are appended safely. I did not find a path that corrupts a valid existing v1 store. The blocker is narrower but important: the parser cannot distinguish "old v1 row, derive v2 fields" from "malformed v2 row, required v2 fields missing", so malformed v2 can silently become a plausible but wrong cost basis.

Tests run: `python -m pytest tests/test_fx_histories_split.py tests/test_portfolio_store_v2.py -q` -> **8 passed**.

## Confirmed Solid

- `load_lots()` is read-only: it parses the file and returns migrated objects, with no write call on the read path (`golden_vector/portfolio/manual_store.py:30`).
- The v1 derivation is correct for valid existing rows: `cost_currency = buy_currency`, `cost_basis_total = shares * buy_price`, `raw_broker_symbol = ticker`, `source_name = "manual"`, and `cost_basis_as_of_date = buy_date` (`golden_vector/portfolio/manual_store.py:152` through `golden_vector/portfolio/manual_store.py:187`).
- `_write_lots()` backs up a valid pre-v2 store before replacing it with schema v2 (`golden_vector/portfolio/manual_store.py:225` through `golden_vector/portfolio/manual_store.py:257`).
- `LatestFoundationSnapshot.fx_histories` is defaulted and opt-in, so existing callers stay unaffected (`golden_vector/app/latest_data.py:22` through `golden_vector/app/latest_data.py:37`, `golden_vector/app/latest_data.py:91` through `golden_vector/app/latest_data.py:100`).
- `include_fx_histories=True` resolves the manifest's run snapshot and uses checked parquet reads, which matches the manifest-resolved data-spine rule (`golden_vector/app/latest_data.py:159` through `golden_vector/app/latest_data.py:170`).
