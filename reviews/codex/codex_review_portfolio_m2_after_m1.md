# Codex Review - Portfolio M2 After M1

**Grade: NEEDS CHANGES before coding M2**

M1 gives us the right architecture: a first-class `golden_vector/portfolio/` package, persisted artifacts, manifest reads, and a serve layer that renders instead of computing. M2 should keep that shape, but the current v4 M2 line is still too compressed for a safe build. The main changes needed are not product changes; they are data-spine details so pence handling, benchmark betas, valuation, and reconciliation do not create hidden duplicate logic or request-path computation.

## Findings

**P0 - The history pence fix is not implementable safely as written because the history standardizer does not receive the feed currency.** The plan says to complete the history-path pence fix through the shared helper (`reviews/codex/claude_portfolio_tool_plan_v4.md:81`), but `standardize_equity_history` currently receives only configured currency (`GBP`) and not Yahoo's feed currency (`GBp`) (`golden_vector/ingestion/standardize.py:18`). The current equity and benchmark history fetchers call only `fetch_history`, then standardize (`golden_vector/ingestion/fetch_equities.py:44`, `golden_vector/ingestion/fetch_benchmarks.py:36`), while the snapshot path is the only path that calls `fetch_fast_info` and therefore sees the case-sensitive `GBp` tag (`golden_vector/ingestion/fetch_market_snapshot.py:52`, `golden_vector/ingestion/standardize.py:149`). Before coding, M2 must specify a single source of price-unit truth for history rows: add explicit `feed_currency`, `price_scale_factor`, and `minor_unit_adjusted` to raw history, have `normalize_equity_history_to_usd` carry those audit fields, and test that `GBp` history is divided once before USD conversion. Do not infer pence from configured currency or symbol suffix alone.

**P0 - Avoid adding a second Yahoo `fast_info` pass unless the plan accepts the cost.** The cleanest pence source is `fast_info.currency`, but naively adding `fetch_fast_info` to `fetch_equity_histories` would duplicate the snapshot fast-info call already made later in the refresh (`golden_vector/ingestion/fetch_market_snapshot.py:53`). For 60+ tickers this is not fatal, but it is the exact kind of hidden refresh cost we have been removing. M2 should decide deliberately: either introduce a shared per-ticker price-unit observation used by both history and snapshot standardization, or accept one extra fast-info call per ticker and record it in stage timings. The important rule is that the conversion still happens in ingestion/normalization, never in portfolio UI code.

**P0 - The typed valuation boundary still needs a concrete API split, not just a principle.** M1 correctly avoids double pence adjustment by passing the already-normalized snapshot price into `value_line(... feed_currency=None)` (`golden_vector/portfolio/pipeline.py:248`, `golden_vector/portfolio/pipeline.py:254`). But `value_line` itself still applies `price_unit_adjustment(input_value.feed_currency or input_value.price_currency)` (`golden_vector/portfolio/valuation.py:30`), so a future caller can accidentally pass an already-major-unit price with `feed_currency="GBp"` and divide again. M2's "harden the typed valuation boundary" should explicitly split raw-feed valuation from already-normalized valuation, for example `value_raw_feed_quote(...)` versus `value_major_unit_price(...)`, or pass a required `PriceUnitAdjustment` object. The portfolio pipeline should call the major-unit path; ingestion should be the only place that calls the raw-feed path.

**P1 - Benchmark betas need their own backend artifact contract and must not clone Tool A output logic.** The plan asks for a `benchmark_betas` step over GDX/GDXJ (`reviews/codex/claude_portfolio_tool_plan_v4.md:84`), but it does not name the exact shared Tool A primitive to reuse. The existing reusable base is `build_structural_weekly_series` / `build_structural_history_frames` (`golden_vector/model/structural.py:169`, `golden_vector/model/structural.py:217`); the full Tool A summary/output builder contains ranking and UI-facing Tool A fields (`golden_vector/model/pipeline.py:321`) and should not be copied into portfolio code. M2 should add a small backend module such as `portfolio/benchmark_betas.py` that reads cached benchmark histories plus gold, calls the shared structural primitive, persists one row per benchmark, and registers `benchmark_betas` in the model-state artifact map. Tests should prove GDX/GDXJ are not added to `universe.yaml`, missing/low-confidence benchmark beta fails closed, and the same weekly calendar rule is used as Tool A.

**P1 - The benchmark-beta input source and refresh ordering are underspecified.** Full refresh currently runs portfolio after `option-artifacts` (`golden_vector/cli.py:3076`), but the `--skip-tool-b` path can run portfolio immediately after Tool A (`golden_vector/cli.py:2977`). Existing benchmark histories are cached through option/benchmark flows, not as a clearly named foundation artifact (`golden_vector/ingestion/options_phase.py:469`, `golden_vector/ingestion/fetch_benchmarks.py:24`). M2 must decide whether `benchmark_betas` is built as an independent portfolio/foundation step that always has its inputs, or whether it is optional and unavailable on partial refreshes. Do not let the portfolio page or hedge card scan raw benchmark files at request time to paper over this ordering gap.

**P1 - Reconciliation should be scaffolded as a backend data-quality contract, not as a broker importer in disguise.** The v4 plan says M2 includes a two-stage reconciliation scaffold (`reviews/codex/claude_portfolio_tool_plan_v4.md:86`), while manual M1 intentionally has no IBKR import. That is fine only if M2 creates a generic `portfolio_reconciliation` schema/status produced by the portfolio pipeline, with Stage 1 marked `MANUAL_ENTRY_NO_BROKER_TOTALS` rather than trying to parse broker files early. Broker CSV parsing, account sections, cash lines, and symbol maps belong to the later import milestone. This keeps M2 backend-only and avoids building a half-importer before Emanuel needs it.

**P1 - Fix percentage naming before M2/M3 consume M1 artifacts.** Claude's M1 review caught that `position_weight_pct` and `pnl_pct_local` store fractions, not percentages. That is currently only cosmetic because the UI formatter multiplies by 100, but M2/M3 will start consuming portfolio artifacts for concentration, NAV weights, and analytics. Rename these to `position_weight_fraction` / `pnl_fraction_local`, or store actual percentage points consistently, before adding more downstream consumers. This is a schema bump, so it belongs at the start of M2 rather than after charts and exports depend on the current names.

**P2 - Reuse the existing artifact writer shape instead of growing a benchmark-specific writer.** Portfolio M1 already has one artifact pair writer (`golden_vector/portfolio/pipeline.py:477`) and the repo has shared atomic parquet writing (`golden_vector/common/parquet.py:126`). M2 should either generalize the portfolio writer for `benchmark_betas` or keep it in one portfolio artifact module. Do not add a third run-stamped parquet writer with slightly different naming, because pruning, manifest resolution, and schema checks will drift.

**P2 - Keep M2 serve-read-only by construction.** The current portfolio page reads via `load_portfolio_data` and renders (`golden_vector/serve/portfolio_page.py:40`), which is the right boundary. M2 should explicitly say that benchmark beta, reconciliation status, and any pence/history checks are computed in refresh/pipeline code only. The serve layer may show fail-closed cards or data issue messages, but it must not read raw history, compute correlations, compute beta, or reconcile broker values.

**P2 - Make portfolio-enabled behavior explicit.** Portfolio artifacts are optional in model state today (`golden_vector/app/model_state.py:373`) and `portfolio.enabled` defaults false (`golden_vector/contracts/config_models.py:928`). M2 should say which parts run always versus only when enabled. The history pence fix is foundation-wide and should always run. `benchmark_betas` is probably portfolio-only for now and can run only when portfolio is enabled, but if Tool C/D or options later reuse it, it should be promoted to a shared benchmark artifact outside `portfolio/`.

## Recommended Revised M2 Shape

1. **M2a - History price-unit contract.** Extend history standardization with explicit feed currency and audit fields, update USD normalization to carry them, and add tests for `GBp` divided once and `GBP` unchanged. Decide up front whether this reuses snapshot fast-info observations or makes one extra fetch per ticker.
2. **M2b - Valuation API hardening + M1 schema cleanup.** Split raw-feed valuation from major-unit valuation, migrate `_pct` artifact columns to self-describing names, and add double-conversion tests covering snapshot-to-portfolio valuation.
3. **M2c - Benchmark betas artifact.** Add `portfolio/benchmark_betas.py`, reuse Tool A structural weekly primitives, persist `benchmark_betas`, register it in the manifest, and fail closed when unavailable. Add refresh-order tests for full and partial refresh behavior.
4. **M2d - Reconciliation scaffold only.** Persist a simple backend status artifact/section that reports manual-entry limitations and future broker-total slots. Do not build IBKR import yet.

## Bottom Line

The architecture direction is right, but M2 needs a tighter build brief before implementation. The critical point is that all new logic stays in ingestion/normalization/pipeline artifacts, not in `serve/`; and that pence, valuation, benchmark beta, and reconciliation each have one shared backend implementation instead of small copies growing around the app.
