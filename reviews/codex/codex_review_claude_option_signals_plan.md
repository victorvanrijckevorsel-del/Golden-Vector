# Codex Review - Claude Option Signals Plan

**Grade: NEEDS CHANGES**

The direction is valuable: backend-computed option-chain signals, sector references via GDX/GDXJ, and visual explanations inside the existing Option Trading surface are the right shape. The plan is not build-ready because three load-bearing parts are underspecified: open-interest "flow" semantics, stale-quote carry-forward semantics, and the persisted artifact contracts. Those are not cosmetic details. They determine whether the tool tells Emanuel something real or quietly mixes stale and fresh data under one current-state manifest.

## Severity-Ordered Findings

**[Blocker] The stale-quote guard conflicts with the current coherent-state model unless carry-forward semantics are designed first.**  
The plan says that if a chain's live bid/ask coverage is low, the refresh should keep the last good option snapshot for that ticker and not overwrite it (`reviews/codex/claude_option_signals_plan.md:45-55`). Today option snapshots and option artifacts are stamped as one run: raw option snapshots are written into the current run manifest (`golden_vector/ingestion/options_phase.py:117-251`), option artifacts carry one `snapshot_refresh_run_id` and `source_run_id` (`golden_vector/hedge/option_artifact_frames.py:293-314`), and model-state alignment expects required option artifacts to reference the current options refresh (`golden_vector/app/model_state.py:645-700`). Per-ticker carry-forward would deliberately mix rows from different option snapshot times inside one published artifact. That can be the right product behavior, but it must be explicit: each carried row needs its own `quote_snapshot_run_id`, `quote_as_of`, `freshness_status`, and UI/status wording, while the manifest must still say the current refresh consumed stale-held option rows. Otherwise "alignment OK" becomes misleading. A simpler first build would fail the option-signal artifact for stale chains and keep the previous complete model state unchanged, then add per-ticker carry-forward only after the manifest/status contract is agreed.

**[Blocker] Open-interest "flow" is overstated and the plan risks calling a weak/public field a strong intraday signal.**  
The plan treats `delta put-OI` and `delta call-OI` as "new money / conviction entering" and says fixed intraday refresh times make OI-change meaningful (`reviews/codex/claude_option_signals_plan.md:19`, `reviews/codex/claude_option_signals_plan.md:24`, `reviews/codex/claude_option_signals_plan.md:48`). Public open interest is normally a post-clearing number, not a live signed flow field; same-day 11:00 vs 14:30 OI deltas can be stale, zero, or vendor-timing noise. Volume is intraday, but it is not signed and does not tell us buy-to-open vs sell-to-close. Before build, rename this component away from "flow" unless we can prove the field timing, compare OI only between distinct OI-as-of sessions, and use `volume / prior OI` or `volume / max(OI, 1)` as the intraday activity context. Also compare OI by stable contract identity, not by "nearest 60d bucket", because rolling from one expiry to another can create fake changes.

**[Blocker] The plan does not define the new option-signal artifact contract, and the serve layer currently reads all registered option artifacts.**  
The architecture says "persisting a per-ticker option-signals artifact" (`reviews/codex/claude_option_signals_plan.md:57-60`), but it does not list artifact names, required/optional status, schema columns, migration behavior, or stale-schema handling. Current option artifacts are centrally registered in `OPTION_ARTIFACT_NAMES` (`golden_vector/contracts/option_artifacts.py:12-21`) and the Option Trading reader loops over every registered artifact through the manifest (`golden_vector/serve/option_trading_data.py:470-481`). Adding a new artifact without a migration plan can make the whole Option Trading surface disappear until a refresh, while making it optional can hide a stale/missing signal silently. The plan needs a concrete schema: likely `option_signal_summary`, `option_signal_history_points`, `option_skew_curve_points`, and `option_oi_strike_points`, each with `schema_version`, `source_run_id`, `snapshot_refresh_run_id`, `quote_snapshot_run_id`, `options_as_of_date`, `ticker`, `benchmark_symbol`, `history_depth`, and status/reason fields. It also needs a stale-artifact test and a calm "run refresh" page/notice if the artifact is missing after migration.

**[Major] "IV rank vs own history" cannot be trusted unless the history source, retention, and minimum sample rules are specified.**  
The plan correctly distinguishes current cross-sectional IV from own-history IV rank (`reviews/codex/claude_option_signals_plan.md:20`, `reviews/codex/claude_option_signals_plan.md:42-43`), but it does not specify how the historical series is built. Existing code only computes `iv_percentile_cross_sectional` on the current feature frame (`golden_vector/features/options.py:152`) and current run artifacts (`golden_vector/hedge/option_artifact_frames.py:45-83`). Run pruning currently treats old output option artifacts and unprotected run dirs as prune candidates (`golden_vector/app/run_pruning.py:232-255`, `golden_vector/app/run_pruning.py:290-318`). If history is a headline component, the plan must define an append-only or retained history store, protect it from pruning, and require a minimum number of clean snapshots before emitting rank/trend labels. Until then, IV rank should be `LIMITED_HISTORY`, not part of the headline.

**[Major] Raw `put_IV - call_IV` is useful, but the decision signal should be a sector-relative 25-delta risk-reversal residual.**  
The existing code already computes `put_iv_25d_{h}d`, `call_iv_25d_{h}d`, and `iv_skew_{h}d = put_IV - call_IV` (`golden_vector/features/options.py:76-80`, `golden_vector/features/options.py:134-138`). That is a good internal convention because positive means downside puts are richer. The signal Emanuel should trust more is: "single-name 25-delta downside skew minus the GDX/GDXJ sector skew at the same horizon." That isolates idiosyncratic fear from broad miner-sector hedging. The plan mentions GDX/GDXJ qualitatively (`reviews/codex/claude_option_signals_plan.md:37-40`) but should make this the headline signal, not a secondary note. It also needs a deterministic benchmark rule: compare every name to GDX, show GDXJ as junior-sector context, or map smaller/junior names to GDXJ by an explicit config field. Do not infer the benchmark ad hoc in the UI.

**[Major] Put/call symmetry is too neat; the bullish and bearish readings need different evidence standards.**  
The plan wants a symmetric rule-based signal across puts and calls (`reviews/codex/claude_option_signals_plan.md:26-33`, `reviews/codex/claude_option_signals_plan.md:62-65`). Mechanically this is clean, but market structure is not symmetric. Equity options commonly have persistent downside skew because crash protection is structurally bid; call richness can mean upside speculation, but it can also reflect earnings/takeover optionality, borrow/dividend effects, wide quotes, or sparse calls. I would keep one shared data model, but render two separate interpretations: **bearish/downside concern** needs sector-relative put richness plus activity/liquidity confirmation; **bullish/upside demand** needs call richness versus puts and sector plus call volume/OI context. Do not let one generic `DOWNSIDE / UPSIDE` classifier imply equal confidence on both sides.

**[Major] Quote-freshness coverage must be measured on the tradable/readable part of the chain, not the whole chain.**  
The stale guard proposes using the fraction of chain contracts with both live bid and ask (`reviews/codex/claude_option_signals_plan.md:50-55`). Whole-chain coverage can be misleading because deep OTM and far-expiry contracts often have zero bids even during market hours. The guard should measure freshness in the relevant DTE/moneyness/delta region used by the signal: e.g. 45-150 DTE, near ATM plus 10-35 delta wings, sane IV, nonzero underlying, and contracts that pass the existing liquidity metric fields (`golden_vector/hedge/options_liquidity.py:90-118`). Store both raw-chain coverage and signal-area coverage, but gate the signal on the signal-area coverage.

**[Major] The chart plan needs normalized chart data, not raw strike curves.**  
The proposed skew curve, skew-over-time, and OI-by-strike charts are useful first cuts (`reviews/codex/claude_option_signals_plan.md:67-72`), but raw strike IV curves are hard for non-experts and sparse miners will produce jagged artifacts. Persist normalized chart points by moneyness or delta bucket, with liquidity flags and the selected benchmark overlay. For a non-expert, the most useful first visual is not a full curve; it is a simple signal card/gauge with four lanes: **Direction** (sector-relative 25-delta skew), **Conviction** (volume/OI activity and OI session change if valid), **Cost** (IV/RV and IV rank when enough history), and **Data quality** (freshness/liquidity/history depth).

**[Medium] Market-hours auto-refresh is product-useful but over-scoped for the first signal build.**  
The plan suggests a Windows Task Scheduler setup helper that runs `python main.py refresh` on US trading days (`reviews/codex/claude_option_signals_plan.md:48`). That is reasonable eventually, but it adds calendar/DST/holiday/setup complexity around a signal whose artifact semantics are not locked yet. I would split this: first build persisted signals, stale detection, and UI labels against manual refresh; then add a documented scheduler/helper after we have one or two clean market-hours refreshes proving Yahoo tolerance and quote coverage. If scheduler ships, it must be explicit that stock/foundation data is daily-close based while option signal data is market-hours snapshot based.

**[Medium] The "blunt, no safe wording" requirement needs guardrails so we do not overstate noisy public data.**  
The plan says no defensive wording (`reviews/codex/claude_option_signals_plan.md:7-12`, `reviews/codex/claude_option_signals_plan.md:72`). I agree with removing fluffy caveats, but the tool must still be precise. Good wording: "AEM puts are priced richer than calls by X vol points, Y above GDX; options are pricing more single-name downside protection." Bad wording: "buyers are betting the stock will fall" unless volume/OI evidence supports that, and even then it is unsigned. Blunt should mean clear and accurate, not more certain than the data.

## What I Would Actually Trust

1. **Headline direction:** 60d and 90d 25-delta downside skew, defined as `put25 IV - call25 IV`, shown both absolute and sector-relative versus GDX/GDXJ. This is the cleanest "what is the options market pricing?" signal.
2. **Idiosyncratic signal:** name skew minus sector ETF skew at the same horizon. A single miner with steep skew while GDX/GDXJ are normal is much more decision-useful than raw skew alone.
3. **Activity confirmation:** current volume-to-OI by side and moneyness band, plus day-over-day/session-over-session OI change only when the prior snapshot is a valid comparable OI session. Treat this as confirmation, not signed flow.
4. **Cost/richness:** ATM IV/RV and IV rank versus own history once enough snapshots exist. This answers "is this option expensive?" rather than "which way is the stock going?"
5. **Static put/call OI ratio:** keep it as context only. It is too crude to drive the signal.

I would not build a black-box composite score. Use a transparent label made from the four components: direction, confirmation, cost, and data quality. Emanuel can then see the reason instead of trusting an opaque number.

## Better Decision-Helping Charts

1. **Per-name signal card/gauge:** one row with four lanes: Direction, Activity, Cost, Data Quality. Each lane shows one number, one label, and one short reason. This should be the first thing on the ticker detail page.
2. **Name-vs-sector skew overlay:** bars or lines for AEM, GDX, and GDXJ at 60d/90d/120d showing 25-delta skew and the residual. This makes "sector-wide fear vs name-specific fear" obvious.
3. **Universe heatmap:** rows are tickers; columns are sector-relative skew, skew change, put activity, call activity, IV/RV, history depth, and liquidity. Sort by downside residual. This is better for scanning all names than a table of raw ratios.
4. **OI/volume strike ladder:** mirrored put/call open interest by strike, with spot marked and today's volume highlighted separately. Do not label OI change as "new money" unless it is a valid session-over-session OI comparison.
5. **Term-structure strip:** ATM IV and skew across 60/90/120 for the name and GDX/GDXJ. This helps answer whether risk is front-loaded or persistent.

## Required Plan Changes Before Build

- Define the exact signal artifacts, schema columns, required/optional status, stale-schema behavior, and model-state manifest registration.
- Decide whether stale quotes block publish entirely or whether per-ticker carry-forward is allowed; if allowed, add row-level quote snapshot identity and status fields.
- Replace "OI flow" wording with an OI/activity model that respects public OI timing and unsigned volume.
- Make sector-relative 25-delta skew the headline metric, with a deterministic GDX/GDXJ benchmark rule.
- Add retention/history design before any IV-rank or skew-trend headline labels.
- Split scheduler/auto-refresh into a second milestone unless the first build explicitly includes holiday/DST tests and Yahoo-tolerance validation.
- Add tests for sparse chains, missing GDX/GDXJ benchmark, stale quotes, artifact migration, no request-path option math, and no silent missing signal fields.

Once those changes are made, I would expect this to become `READY WITH MINOR CHANGES` or `READY`; the concept is good, but the current plan is still too loose around the parts that make the signal trustworthy.
