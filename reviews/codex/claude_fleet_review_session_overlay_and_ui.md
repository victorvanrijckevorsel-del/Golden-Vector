### [MEDIUM] OVL2 Percent-change recomputed in JS (business math in serve/JS, duplicates server logic)
- file: golden_vector/serve/static/overlay-crosshair.js:8-11, 79  (dim=overlay-crosshair-js)
- desc: fmtPct computes `pct = value - base` then formats it. The values are rebased to base=100, so `value - base` is the displayed metric 'percent change since the rebase start' — i.e. business math computing a % in JS. CLAUDE.md allows pure pixel-mapping and string formatting but explicitly forbids 'computing a %'. Worse, the server ALREADY computes the same subtraction for the y-axis gridline labels (charts.py line 381 `pct = tick - base`), so this is a second, divergent copy of the same logic (the 'one copy of everything' rule). The two formatters even disagree on precision/sign: gridlines use `{pct:+.0f}%` (always-signed) while fmtPct uses toFixed(0) with a manual '+' only for >=0, and they round independently — a drift risk.
- fix: Move the % to the backend: have charts.py emit the formatted pct string (and/or the numeric pct) inside each byDate entry, e.g. byDate[date] = [y_px, value, pct_label], reusing the SAME formatter used for the gridline labels. JS then only reads and renders the pre-formatted string, eliminating both the JS arithmetic and the duplicate/diverging logic.
- verdict: I was asked to refute this, but every technical claim checks out against the live code, so the honest verdict is CONFIRMED.

1) JS arithmetic in serve (REAL): overlay-crosshair.js:8-11 has `function fmtPct(value, base) { var pct = value - base; return (pct >= 0 ? "+" : "") + pct.toFixed(0) + "%"; }`, used at line 79 in the hover tooltip. The values are rebased to base=100 upstream (charts.py:279 `base: float = 100.0`; docstring at 281-287 says values are pre-rebased), so `value - base` IS the "percent change since rebase start" — business arithmetic. The file lives in golden_vector/serve/static/, which is the serve layer. CLAUDE.md's #1 "Where code lives" rule forbids "arithmetic, ratio math ... in serve/ or templates." The file's own header comment ("no business math in JS") is therefore inaccurate.

2) Duplicate/divergent copy (REAL): charts.py:381 computes the SAME subtraction `pct = tick - base` and formats it at line 382 as `f"{pct:+.0f}%"` for the y-axis gridline labels. Grep confirms these are the only two `- base` percent computations in the codebase; there is no shared helper. So the same "% change since rebase" transformation exists in two independent copies — the "one copy of everything" canon violation.

3) Drift is demonstrable, not theoretical: I ran both. Python `f"{120.5:+.0f}"` -> "+120" (round-half-to-even) and `f"{-0.5:+.0f}"` -> "-0", while JS `(120.5).toFixed(0)` -> "121" and `(-0.5).toFixed(0)` -> "-1". The two formatters genuinely round differently at .5 boundaries, and the sign style differs (Python `+` flag always-signs incl. +0%; JS only prepends + when pct>=0). Real divergence.

4) No guardrail covers it: the serve-arithmetic sweep (test_workspace_app.py:2873) globs only `golden_vector/serve/*.py` and its token list targets pandas/numpy ops, so neither the JS file nor a bare `-` subtraction is scanned. The arithmetic sits in an untested gap.

Severity: keeping MEDIUM (as filed). It is a genuine violation of the repo's most-emphasized canon (backend computes / serve renders, one copy of everything), in a blind spot of the guardrail tests, with a demonstrated drift mechanism. I considered downgrading to LOW/NIT because the live user-facing impact is small — the rounding only diverges at exact .5 boundaries, and the gridline vs tooltip render different element types so a user rarely sees the same number both ways, and the tooltip also prints the raw value (pt[1].toFixed(1)). But the category is exactly what the canon (and dedicated guardrail tests) exist to prevent, so MEDIUM is appropriate rather than a nit. The suggested fix is sound: emit a formatted/numeric pct inside each byDate entry from charts.py reusing the gridline formatter, so JS only renders a pre-formatted string.
